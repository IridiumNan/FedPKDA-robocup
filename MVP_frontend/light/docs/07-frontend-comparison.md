# 前端方案对比分析

> 对比 legacy 前端与 MVP 设计方案，评估两个方案对比赛目标的支撑能力。

## 一、两个方案概述

### Legacy 前端

纯 HTML 静态页面，暗色科技风（玻璃面板、辉光动画、网格背景）。6 个页面：首页、仪表盘、客户端管理、联邦训练、隐私策略、审计日志。所有数据硬编码在 HTML 中，无交互逻辑、无数据绑定。

### MVP 设计方案

基于产品设计流程产出的交互原型（`MVP_frontend/light/`）。亮色企业风格，信息架构围绕两个角色（协调员/运营员）的日常工作流设计。协调员端 4 页（事件中心、节点管理、训练控制、系统架构），运营员端 3 页（节点状态、训练控制、系统架构）。使用 JS 动态渲染数据，支持交互操作（展开详情、广播通知、标记已处理）。

## 二、逐维对比

### 2.1 信息架构

| 维度 | Legacy | MVP |
| --- | --- | --- |
| 页面划分依据 | 功能模块（仪表盘/训练/客户端管理） | 角色工作流（协调员日常巡检/运营员节点维护） |
| 信息组织 | FL 通用术语（ε 预算、全局准确率、轮次） | 运营语言（行为评分、检测率趋势、节点异常告警） |
| 角色权限 | 无区分 | 两角色完全隔离，同一页面不同信息范围 |
| 信息密度 | 低（一屏 4-6 个指标卡即填满） | 高（事件中心 14 条事件可扫描，节点管理 24 机构表格） |
| 可扫描性 | 差——所有信息平铺，无优先级 | 好——渐进式展开，默认只显示标题 |

**结论**：Legacy 的信息架构是"功能模块列表"，MVP 的是"角色工作台"。前者适合展示系统有哪些模块，后者适合让人每天打开系统完成工作。

### 2.2 视觉效果

| 维度 | Legacy | MVP |
| --- | --- | --- |
| 风格 | 暗色赛博朋克（玻璃+辉光+网格背景） | 亮色企业 SaaS（白底+蓝色调+微阴影） |
| 第一印象 | 像安全产品，"看起来很厉害" | 像内部工具，"看起来很干净" |
| 视觉密度 | 低——大量空间被装饰元素占用 | 中——信息密度高但通过留白和间距保持可读性 |
| 动画/特效 | 辉光、脉冲、渐变边框、悬停上浮 | 无多余动画，悬停仅有颜色/边框变化 |
| 辨识度 | 高——与大多数比赛作品区分度大 | 中——与常见 SaaS 产品接近 |

**结论**：Legacy 在视觉上更"炫"。MVP 在视觉上更"可用"。哪种更有价值取决于评判标准——如果评委只看一眼截图，legacy 赢。如果评委点开页面操作，MVP 赢。

### 2.3 与算法的关联

| 维度 | Legacy | MVP |
| --- | --- | --- |
| 算法映射 | 无。数据都是编造的，没有出处 | 每项展示数据有算法来源（马氏距离→行为评分，Fisher→贡献度等） |
| 参数面板 | 无操作逻辑 | 训练控制页的 global_par / join_ratio / 异常阈值直接对应 FedPKDA 可调参数 |
| 实验数据 | 无 | 检测率趋势图使用真实跑完的四组 Cifar100 实验结果 |
| 自圆其说 | 需要编造故事来解释数据来源 | 不需要——每条数据的来源在 `frontend_plan.md` 中有完整映射 |

**结论**：Legacy 是一组好看的页面，跟 FedPKDA 算法没有实质性关联。MVP 的每个信息元素都能追溯到算法的具体计算步骤。比赛如果被问到"这个数字怎么来的"，只有 MVP 能回答。

### 2.4 比赛要求匹配度

| 评分维度 | 分值 | Legacy 得分 | MVP 得分 | 说明 |
| --- | --- | --- | --- | --- |
| PPT 与答辩表现 | 25 | 中 | 高 | MVP 有完整的设计逻辑链可以讲述 |
| 创新性/完整性/可实现性 | 25 | 低 | 中 | Legacy 缺少算法关联和角色设计 |
| 专利/软著/论文 | 15 | — | — | 两者依赖同一算法 |
| 市场调研和可行性分析 | 10 | 低 | 高 | MVP 有 ISAC 调研和权力分配分析 |
| 具有推广应用价值 | 10 | 低 | 高 | MVP 面向真实联盟场景，有利益分析 |
| 说明书规范 | 10 | 低 | 高 | MVP 有 `frontend_plan.md` 作为说明文档 |
| 符合主题要求 | 5 | 低 | 高 | MVP 聚焦网络安全，legacy 泛化了场景 |

**结论**：在答辩、创新、调研、推广、文档五个可争取的评分维度上，MVP 的设计逻辑提供了更多可讲述的内容。

## 三、可行性分析：哪个方案能让比赛走得更远？

### 3.1 当前阶段（初赛：文档 + Demo）

两个方案都能提交。Legacy 作为一个"好看的演示"可以过关。MVP 作为一个"有设计逻辑的演示"也可以过关。

**差异在于答辩**：评委问"你们的系统给谁用？为什么这样设计？用什么数据验证的？"——Legacy 需要现场编，MVP 可以直接引用文档中的设计决策。

### 3.2 后续阶段（需要可运行代码）

两个方案都面临同样的问题：后端不可运行。但 MVP 的优势在于——从原型中可以直接推导出后端接口定义（原型上每个数字对应一个 API 端点），这是 `frontend_plan.md` 中已经做好的映射。Legacy 需要从头梳理"每个数字应该从哪个接口来"。

### 3.3 团队能力匹配

团队中有一个会前端的成员。Legacy 需要此人修改 HTML/CSS 去适配内容——但 legacy 的内联 CSS 体量大（每页 500-800 行），修改成本高。MVP 的 CSS 共享在 `style.css`（200 行），修改成本低。

## 四、设计哲学差异

### Legacy 的设计假设

"看起来厉害 = 真的好。"大量视觉装饰、FL 学术术语、硬编码的假数据。面向的观众是"扫一眼屏幕就觉得这个东西很厉害"的人。

### MVP 的设计假设

"能用 = 真的好。"信息有来源、操作有反馈、角色有边界、算法有映射。面向的观众是"想知道这个系统到底怎么工作"的人。

**两者不可兼得。** 视觉装饰会吃掉实际信息空间。信息密度会削弱视觉冲击力。这是一个零和博弈——你无法同时满足"3 秒截图看起来很炫"和"30 秒操作体验很好"。

### 我们的选择

我们在这个项目中选择的是第二个方向。不是因为它更好看——它确实没有 legacy 好看。是因为**比赛考查的不是截图，是答辩时的逻辑链**。如果评委问"你们的设计有什么创新"，我们能回答——技术信任替代法律信任、协调员权力退化、数据不出本地。

## 五、总结

| | Legacy | MVP |
| --- | --- | --- |
| 视觉冲击 | 高 | 中 |
| 信息可用性 | 低 | 高 |
| 算法关联 | 无 | 每项可追溯 |
| 角色设计 | 无 | 两角色完全隔离 |
| 答辩可讲内容 | 少——需编造 | 多——有完整设计文档支撑 |
| 前端修改成本 | 高（内联 CSS） | 低（共享 CSS） |
| 适合的场景 | 截图展示、第一印象 | 答辩讲述、功能演示 |
| 核心风险 | 被问住后无法自圆其说 | 视觉"不够酷"被认为水平不够 |

**Legacy 最大的风险**：在答辩环节，评委问到"系统怎么做权限隔离的？数据怎么保证不出本地？行为评分怎么计算的？"——legacy 无法回答，因为这些设计根本不在其中。

**MVP 最大的风险**：视觉上不够炫，被评委或团队认为"没用心做界面"，但实际上信息架构的设计投入远超 legacy。
